TREL Thrust Vector Control System

From a 5,000 lb-rated gimbal test stand in SOLIDWORKS to real-time embedded TVC software on an NI sbRIO.

Overview

When I joined the Texas Rocket Engineering Lab (TREL), I actually started on the mechanical side. My first project was helping design a 5,000 lb-rated gimbal test stand in SOLIDWORKS to reproduce loads expected on our thrust vector control hardware. Going through design reviews with aerospace-industry mentors taught me how load paths, fasteners, structural margins, and mechanical constraints ultimately affect the software and controls built around the hardware.

From there I shifted into what I enjoyed most: embedded software and control. I started with basic actuator bring-up on an Arduino before moving the system onto an NI sbRIO-9637 running NI Linux Real-Time, where I developed C/C++ control software for a 2-axis TVC system. The control loop ran at 100 Hz, consuming desired pitch and yaw commands from the rocket's shared Data Vector, tracking brushed-DC linear actuator motion through Hall-effect feedback, and commanding the motor drivers to extend, retract, or stop each actuator.

I also worked on a propulsion valve-control state machine for pressurization, chill-down, purge, and abort sequencing, and used Bash tooling to support software deployment across the rocket's flight computers. Working across GNC, avionics, and structures made the project a crash course in connecting software decisions to real hardware behavior.

How It Works

The TVC system uses two brushed-DC linear actuators to push and pull on the gimbal linkage, rotating the engine about its pitch and yaw axes. The software closes the loop around actuator position so guidance commands can be translated into controlled physical gimbal motion.

  • Command path: GNC produces desired pitch and yaw commands exposed through the shared Data Vector using fields such as DataVector::PitchDesAngle and DataVector::YawDesAngle.
  • Control loop: C++ software on the sbRIO runs at 100 Hz, giving the controller a nominal 10 ms update period to read the latest command and actuator state, apply control logic, and update the motor command.
  • Actuator feedback: Integrated Hall-effect sensors generate digital pulses as the actuator's internal mechanism moves. Starting from a known reference position, those pulses are counted to track actuator travel and relate it back to gimbal position.
  • Actuator control: The sbRIO sends low-power digital commands to a bidirectional motor driver, which controls the higher-current supply to each brushed-DC actuator. Reversing motor direction produces extend or retract motion, while disabling the drive stops the actuator.
  • Safety limits: Desired commands are bounded by actuator position and rate limits before reaching the hardware, keeping gimbal motion inside the permitted mechanical operating range.
  • Valve state machine: A finite-state machine coordinates propulsion-fluid sequencing through pressurization, chill-down, purge, and abort states.
  • Deployment: The control software runs under NI Linux Real-Time, with Bash scripts used to automate deployment and synchronization across multiple flight computers.

The result is a hardware-software control chain where a desired attitude command from GNC moves through the vehicle data interface, into a real-time C++ control loop, and ultimately becomes physical engine-gimbal motion with actuator feedback closing the loop.
